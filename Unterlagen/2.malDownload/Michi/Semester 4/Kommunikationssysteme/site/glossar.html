    Callback

    Callables (Funktionen oder Methoden) die (exakt: Übergeben wird deren Name und damit deren Adresse, also ein Function-Pointer würde man in C| sagen.) Programmteilen übergeben werden können, damit jene diese bei Bedarf ausführen können. Siehe :ref:seminars.S:(!) Klassenhierarchie Sensoren für eine Musterlösung.

    CLI

    Command-Line-Interface.

    Context-Manager

    Siehe https://docs.python.org/3/reference/compound_stmts.html#with und https://docs.python.org/3/library/contextlib.html (oder auch https://realpython.com/python-with-statement/#using-the-python-with-statement).

    Sie können Ihre eigenen Context-Manager schreiben. Nehmen Sie an, Sie wollten eine Klasse Sensor schreiben, die man öffnen und schließen muss, wenn man mit ihr arbeiten will, also

    with Sensor( "sensor 1") as sensor:
    sensor.write_to_hardware()
    sensor.read_from_hardware()

dann können Sie die Klasse so implementieren::

class Sensor:
    def __init__( self, id):
        self.__id = id

    def __enter__( self):
        self.open()
        return self

    def __exit__( self, type, value, traceback):
        self.close()

    # Ab hier alle Ihre weiteren Methoden wie 
    #   open, write_to_hardware, read_from_hardware, close.

    Wird der with-Block betreten, wird __enter__ ausgeführt und damit der Sensor für die weitere Kommunikation geöffnet.

    Wird der with-Block verlassen, wird __exit__ nd damit close auf jeden Fall ausgeführt.

    Dtor

    Kurz für Destructor. Hat in Python sehr untergeordnete Bedeutung, weil Ressourcen automatisch freigegeben werden (nicht so in C++!).

    Duck-Typing

    Duck-Typing bezeichnet eine Art Prinzip in der Programmierung mit Python: If it walks like a duck and if it quacks like a duck, it is a duck. Es reicht also, wenn alle Methoden mehrerer Klassen gleich vorhanden sind (Signatur), die Klassen müssen nicht von einer gemeinsamen Basisklasse abgeleitet sein. In statisch typisierten Programmiersprachen müssten die Sensoren alle von einer Basisklasse abgeleitet sein.

    LoD

    The Law of Demeter. Dieses Gesetz, nein, lassen Sie uns es als Richtlinie bezeichnen, besagt, "dass Objekte nur mit Objekten in ihrer unmittelbaren Umgebung kommunizieren sollen. Dadurch soll die Kopplung (das heißt die Anzahl von Abhängigkeiten) in einem Softwaresystem verringert und somit die Wartbarkeit erhöht werden. Es wird deswegen manchmal auch als „Prinzip der Verschwiegenheit“ bezeichnet. [https://de.wikipedia.org/wiki/Gesetz_von_Demeter]". Man kann es gut zusammenfassen mit den folgenden 3 Statements (https://en.wikipedia.org/wiki/Law_of_Demeter):

    • Each unit should have only limited knowledge about other units: only units "closely" related to the current unit.
    • Each unit should only talk to its friends; don't talk to strangers.
    • Only talk to your immediate friends.

    LSP

    "Liskov Substitution Principle". Dieses Prinzip besagt, "dass ein Programm, das Objekte einer Basisklasse T verwendet, auch mit Objekten der davon abgeleiteten Klasse S korrekt funktionieren muss, ohne dabei das Programm zu verändern. [https://de.wikipedia.org/wiki/Liskovsches_Substitutionsprinzip]". Der Artikel ist es wert, bis zum Schluss gelesen zu werden. Lassen Sie die Diskussion, ob ein Kreis eine spzielle Ellipse ist, auf sich wirken. Sie werden Nutze darazus ziehen, wenn Sie die nächste (hoffentlich nicht zu tiefe) Klassen-Keirarchie entwerfen.

    Message Queuing Telemetry Transport. MQTT "ist ein offenes Netzwerkprotokoll für Machine-to-Machine-Kommunikation (M2M), das die Übertragung von Telemetriedaten in Form von Nachrichten zwischen Geräten ermöglicht, trotz hoher Verzögerungen oder beschränkter Netzwerke.[1] Entsprechende Geräte reichen von Sensoren und Aktoren, Mobiltelefonen, Eingebetteten Systemen in Fahrzeugen oder Laptops bis zu voll entwickelten Rechnern. [https://de.wikipedia.org/wiki/MQTT]"

    SPOT steht für Single point od truth (s. auch DRY) und meint "Wiederholen Sie sich nicht!". Wenn estwas ein Konzept ist, dann machen Sie ein Klasse daraus. Tun Sie das nicht, haben Sie potenziell an vielen Stellen den gleichen Code, den Sie auch überall separat warten müssen!

    Wiederverwendbarkeit

    Kann man auf 2 Arten verstehen.

    1. Man kann darunter verstehen, dass eine Klasse durch eine entsprechende Ableitung erweitert oder spezialisiert wird. Zu programmieren ist dann nur der Unterschied zur Base Class.

    2. Man kann Wiederverwendbarkeit aber auch von der anderen Seite her sehen. Hat bspw. einen Programmteil, der Sensoren liest, so ist dieser Teil im weiteren Sinne wiederverwendbar, wenn ein neuer Sensor hinzukommt. Der neue Sensor muss dazu nur das Interface Base Class implementieren.
