    Einleitung

    .. _DISTRIBUTED COMPUTING / Einleitung:

    Python hat so seine Schwächen, wenn es um die parallele Ausführung von Code geht. Das Mittel der Wahl, um Code wegen Laufzeiteinsparungen parallel auszuführen, sind Threads. Wegen des Global Interpreter Lock (GIL) <https://wiki.python.org/moin/GlobalInterpreterLock>_ braucht die Ausführung von Funktionlität in Threads mehr Zeit als die serielle Ausführung und ist damit "nur" ein Mittel der Strukturierung eines Programms.

    Wenn's wirklich um Performance geht, muss man andere Lösungen suchen - und die gibt's auch. Im Folgenden wollen wir die wichtigsten beleuchten, wobei die Aufstellung alphabetisch ist:

    multiprocessing

    Python bietet in der Standard Library das Package multiprocessing <https://docs.python.org/3/library/multiprocessing.html>_, das Multiprocessing unterstützt. Mit diesem Package ist es möglich, Code auf einem anderen Prozessor (Kern eines Prozessors) ausführen zu lassen. Denn bekanntermaßen hat das Multithreading unter Python seine Schwächen, bringt nicht den erwarteten Performance-Gewinn, weil die Threads nicht auf die vorhandenen Kerne eines modernen Prozessors verteilt werden.

    Echtes Multithreading bietet Python eingebaut also nur mit diesem Package. Man kann sich aber leicht vorstellen, dass das nicht gratis ist insofern, als das Überschreiten von Prozessgrenzen im Vergleich zum Arbeiten mit Threads laufzeitintensiv ist.

    Und das wollen wir jetzt messen. Wir schreiben ein Programm, das einen Prozess erzeugt, ihn startet und dann auf seine Beendigung wartet. Die Kommunikation über eine Queue oder eine Pipe lassen wir weg.

    FAQ

    Welche der genannten Methoden und Verfahren verlangt den geringsten Aufwand?

    Man muss unterscheiden in Verfahren, die in der |py|_-Welt bleiben und solche, die es erlauben, Code anderer Sprachen zu integrieren.

    Verfahren, die in der |py|_-Welt bleiben - Pyro5 macht hier eine sehr gute Figur. - RPyC funktioniert konzeptionell ähnlich wie Pyro5, ist aber umständlich beim Verbinden mit einem RPyC-Server. - Ray scheint mit wirklich wenig Aufwand Mutliprocessing zu ermöglichen und - und das ist sehr wichtig - die nötige Interprozess-Kommunikation, die bei multiprocessing sehr eingeschränkt ist.

    Leider konnte der Authot doeser Zeilen Ray nicht ausprobieren, weil er auf einer Rolling Realeas arbeitet und Ray immer 1 - 2 Versionenen hinterherhinkt. Unter Windows oder einer Distro, die nur aale paar Monate aktuelisiert werden kann, durchaus einen *genauenÜ* Blick wert!

    Verfahren, die andere Sprachen integrieren - Die Integration mit Nim <https://nim-lang.org/>_ verlangt sehr wenig Aufwand wegen des Packages nimpy.

    -   Ebenso verlangt `Cython <https://cython.org/>`_ sehr wenig AUfwand. Hie rmuss man allerdings bedenken, dass man |c| programmieren muss, wenn man den vollen Laufzeitvorteil lukrieren will.

    Und eine Mischung von beidem - Hier würde man wohl gRPC nennen müssen, das es erlaubt, RPC-Server zu schrieben in einer beinahe beliebigen Sprache. Der Autor dieses Dokuments hat gut Erfahrungen mit diesem Pake gemacht. Das liegt sicher sicherlich ausch an dem Protkoll, das gRPC unterstützt und den Tools, mit diesem Protokoll zu arbeiten.
