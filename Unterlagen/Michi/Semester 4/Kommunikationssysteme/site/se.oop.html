    Abstract Base Classes

    Führen Sie folgendes Programm aus und diskutieren Sie den Output. Wofür sind Abstract Base Classes - oder kurz SBC - gut?

    #!/usr/bin/python
# -*- coding: utf-8 -*-

import abc


class Baseclass( abc.ABC):

    @abc.abstractmethod
    def meth( self):
        print( "This is the Baseclass' 'meth'.")
        return


class Subclass( Baseclass):

    def meth( self): # override
        super().meth()
        print( "This is the Subclass' 'meth'.")
        return


sub = Subclass()
sub.meth()

base = Baseclass()
base.meth()

    ABC erzwingen also ein Interface und das bereits bei der Instanzierung. So kann verhindert werden, dass erst später im Programm, bei Zugriff auf eine nicht implementierte Methode festgestellt wird, dass diese Methide nicht implementiert worden ist.

    Aber kann eine Base Class nicht selbst eine Implementierung der fraglichen Methode liefern? Nicht unbedingt. Wenn sie's kann, dann wird die Methode nicht abstrakt sein müssen, kann aber in abgeleiteten Klassen immer überschrieben werden. Wenn sie es nicht kann, dann muss sie es erzwingen.

    Vor der Verfügbarkeit von ABC konnte man das so erledigen:

    def abstract_method( self):
    raise NotImplementedError()

    Großer Nachteil: Erst bei Zugriff auf diese Methode, irgendwo spät im Programmlauf, ist das Fehlen einer Ableitung festgestellt worden!

    class Sensor( abc.ABC):

    """Base Class aller Sensoren und damit *das* Interface zu allen Sensoren.

    **Die Herausforderung:** Ein Interface zu finden, das zukunftssicher ist.

    **Lohn der Mühen:** Wir programmieren für die Zukunft - [Wiederverwendbarkeit](glossar.html#wiederverwendbarkeit)
    mal anders gedacht!

    Das kann so aussehen:

    -   Jeder Sensor muss potenziell getriggert werden - `write`.
    -   Jeder Sensor muss gelesen werden können - `read`.
    -   Alle Sensor-Daten müssen irgendwie verarbeitet werden können - `read`.
    -   Das Ergebnis muss abgefragt werden können - `value`.

    Example
        ```python
        sensor = SensorUs( "uss.1")
        sensor.write()
        sensor.read()
        value = sensor.value()
        ```
    """

    def __init__( self, id):
        self.__id = id
        self.__value = None
        return

    def id( self) -> str:
        """Eindeutige Id des Sensors, falls er in eine DB (z.B. ein Dict) abgelegt werden können muss.
        """
        return self.__id

    @abc.abstractmethod
    def write( self):
        """Triggern des Sensors, damit er eine Messung vornimmt.

        Hätten diese Methode auch trigger() nennen können. Warum haben wir das nicht?

        Diese Methode ist abstrakt, weil wir nicht wissen können, welcher Sensor wie
        getriggert wird. Wir wissen nicht einmal, ob **jeder** Sensor getriggert werden
        muss.
        """
        pass

    def log_sensorvalue( self):
        """Schreibt :meth:`value` in ein File, dessen Name aus der :meth:`id` abgeleitet wird.
        """
        fn = "./%s.txt" % self.id()
        with open( fn, "a") as f:
            f.write( "%s\n" % self.value())

        return

    def read( self):
        """Lesen des Sensors.

        Allerdings leisten wir uns in dieser Methode den Luxus des Protokollierens des gelesenen
        Wertes. Daher machen wir fürs effektive Lesen einen Downcall nach :meth:`_read_sensorvalue_`.

        2DO:
            Überlegen:

            -   Soll diese Methode gleich auch einen Zahlenwert liefern? Würde sie dann noch ``read``
                heißen können?
            -   Darf eine Methode, die ``read``heißt, loggen?
        """
        self._read_sensorvalue_()
        self.log_sensorvalue()
        return

    @abc.abstractmethod
    def _read_sensorvalue_( self):
        """Sensorwert lesen.

        Diese Methode ist abstrakt, weil wir nicht wissen können, welcher Sensor wie
        getriggert wird. Wir wissen nicht einmal, ob **jeder** Sensor getriggert werden
        muss.
        """
        pass

    def value( self, arg=None):
        """Nach einem `read` kann der Wert mit dieser Methode gelesen werden, den der Sensor gemessen hat.
        """
        if arg is None:
            return self.__value

        self.__value = arg
        return self

import time

from sensors import _Sensors

t = time.time()
while time.time() - t <= 5:
    dt = time.time()
    for sensor in _Sensors:
        sensor.write()
        sensor.read()

        print( "Sensor '%s': %.3f\n" % (sensor.id(), sensor.value()))

    dt = time.time() - dt        
    time.sleep( max( 0, 1.0 - dt))

    Sensoren - Erweiterung

    Randbedingungen

    Die Sensorerweiterungen müssen in abgeleiteten Klassen realisiert werden, die Klassen SensorIr und SensorUs, von denen abgeleitet wird, dürfen nicht verändert werden!

    Das Sensor-Beispiel soll nun erweitert werden insofern, als der Sensor-Manager in der Lage sein soll, auf bestimmte Konditionen wie zu geringe Abstände oder Übertemperatur reagieren können soll. Solche Reaktionen müssen nicht vom Sensortyp, sondern können auch von der Montagelage des Sensors abhängen.

    Rufen Sie sich dabei in Erinnerung, dass der Sensorman keine Kenntnisse von speziellen Fähigkeiten der Sensoren hat, die er ausführt.

    Hinweis

    Erzeugen Sie die beiden Files sensors2.py und sensorman2.py und programmieren Sie hier entsprechend die Lösungen.

    class SensorIr2( SensorIr):

    """Wie Base Class, kann aber im Unterschied zur Base Class Callbacks ausführen, wenn bestimmte Bedingungen erfüllt sind.

    Parameters:
        id (str):
            Identifikation des Sensors.

        panicvalue (any):
            Wie klein darf der Wert werden, bevor der zugehörige :term:`Callback` ausgeführt wird?

        on_panic (callable):
            Funktion oder Methode, die ausgeführt werden soll, wenn der ``panicvalue`` unterschritten wird.


    Rev. Hist.:

        -   **2022-05-15/FGE**: Dokumentation.
    """

    def __init__( self, id, panicvalue=1, on_panic: callable=None):
        super().__init__( id)

        self.__panicvalue = panicvalue
        self._on_panic_ = on_panic
        return

    def read( self): # Override
        """Lesen des Sensors und Ausführen eines :term:`Callbacks`, wenn der Messwert zu klein ist.

        Wir führen hier die Methode der Base Class aus und dann das, was wir hier anders
        oder zusätzlich machen möchten: :meth:`_on_panic_`, wenn der Wert zu klein ist.
        """
        super().read()

        if self._on_panic_ and self.value() <= self.__panicvalue:
            self._on_panic_()

        return

    read()

    class Garage:

        self.__autos = []
        return

    def auto_einstellen( self, auto: Auto):
        if self.__autos.count( auto):
            print( "Sorry, dieses Auto steht schon in der Garage.")

        self.__autos.append( auto)
        return

    def startanleitung_aller_autos( self, renderer: callable=None):
        s = ""
        for auto in self.__autos:
            s += auto.startanleitung()
            s += "\n"

        if renderer:
            renderer( s)

        return s
